# Architectural Decisions

| # | Decision | Why | Risks | Alternatives |
|---|---|---|---|---|
| 1 | Do the migration in layers; **rename layer first** with no logic change | Keeps the API deployable at every step and makes each diff reviewable | Names (`Property`, `Agent`) stay misleading until layer 3 | One big-bang rewrite: faster on paper, hard to debug |
| 2 | Keep GraphQL operations and **MongoDB collections unchanged** in layer 1 | Existing clients and data keep working; no migration script | Frontend still sees real-estate names | Rename now plus a data migration: cleaner, riskier |
| 3 | Use `git mv` for the app folders | Preserves file history across the rename | None meaningful | Copy and delete: loses blame |
| 4 | Keep the `apps/<name>/src/libs` structure and absolute `apps/...` imports | Changing structure is out of scope for a rename | Absolute imports tie code to the folder name (they had to be edited) | Extract a top-level `libs/` with path aliases; do it later with layer 2 |
| 5 | Fix the batch e2e spec to import `BatchModule` | The spec referenced `NestarBatchModule`, which never existed, so tsc already failed on it | The spec may still not pass at runtime (needs Mongo); only compilation was checked | Delete the spec |
| 6 | Run lint **without `--fix`** | `npm run lint` rewrites files; the baseline has 2379 prettier errors that would pollute a rename diff | Lint debt remains | Run prettier over the repo as its own commit (recommended later) |
| 7 | Leave `.env` keys/values alone | No Nestar strings in it; changing DB names would point at different data | None | Rename DB names with a migration |
| 8 | Git identity stays `Kenneth <avazqudratovv@gmail.com>` (global git config), separate from the Claude account email | Commits should match the GitHub account; the signup email is not a git identity | Commits may not link to the GitHub profile if that email is not added to the account | Set a repo-local `user.email` |
| 9 | Treat the target as **Ticketzy** (the request text said "Petoria") | Repo, remote and package name are Ticketzy | If Petoria is a real second rename, the docs need updating | Ask before proceeding |
| 10 | Property becomes **Event + Venue + TicketType** (planned) | Price tiers and capacity do not fit a single `propertyPrice`; locations should be entities, not a Korean-city enum | Large change touching DTOs, sort whitelists, `$lookup`s, batch jobs | Reuse Property with renamed fields: smaller, but keeps the wrong data model |
| 11 | Agent becomes **Organizer** (planned) | Same "owner of listings" role | `MemberType` enum change affects `RolesGuard`, JWT contents and the frontend | Keep AGENT internally and alias in the UI |
| 12 | Order/Ticket need **atomic inventory** (planned) | No inventory logic exists; overselling is the main ticketing risk | Needs conditional `findOneAndUpdate` or transactions (replica set) | Optimistic checks only: race conditions |
| 13 | **`MemberType` stays `USER / AGENT / ADMIN`**; the ER's `ORGANIZER` is not introduced. `events.organizerId` references a member of type `AGENT` | Explicit instruction from the owner | The ER diagram and the earlier docs say ORGANIZER; the field is named `organizerId` while the role is `AGENT` | Rename the role (B7), now cancelled |
| 14 | Event enums: `EventCategory` = CONCERT, SPORT, THEATER, CONFERENCE, FESTIVAL, OTHER; `EventStatus` = DRAFT, PUBLISHED, ON_SALE, SOLD_OUT, CANCELLED, FINISHED, DELETE; `VenueType` = STADIUM, THEATER, CLUB, HALL, OPEN_AIR, ONLINE; `VenueStatus` = ACTIVE, CLOSED, DELETE. Ticket enums: `TicketTypeStatus` = ACTIVE, PAUSED, SOLD_OUT; `TicketCurrency` = USD, EUR, KRW, UZS; `OrderStatus` = PENDING, PAID, CANCELLED, EXPIRED, REFUNDED; `TicketStatus` = VALID, USED, REFUNDED, CANCELLED; `PaymentProvider` = MANUAL, STRIPE, PAYME, CLICK; `PaymentStatus` = INITIATED, CAPTURED, FAILED, REFUNDED | Taken from the owner's ER diagram | Values are first proposals; adding values later is cheap, removing them is not | Free-text categories |
| 15 | Locations are `venues` documents, not an enum; events filter by `venueId` or `cityList` (resolved through venues) | A city enum cannot hold addresses or capacity | One extra lookup per list | Keep a city enum |
| 16 | Payments are a **manual stub** in this milestone: `payOrder` flips PENDING to PAID and writes a `MANUAL` payment | No provider chosen; keeps the inventory and ticket flow testable | Anyone who can call `payOrder` on their own order gets tickets; a real provider webhook must replace it before production | Integrate a provider now |
| 17 | Stock is held by incrementing `ticketTypes.soldQuantity` in one conditional `findOneAndUpdate` (stock, ACTIVE status, sale window and `maxPerOrder` all in the filter). PENDING orders hold stock for 15 minutes (`ORDER_HOLD_MINUTES`); the batch job expires them and releases it | Prevents overselling without transactions or a replica set | `soldQuantity` includes unpaid holds | A separate `reservedQuantity` field |
| 18 | The `properties` collection and `uploads/property/` are **left untouched**; new collections start empty, no migration | Owner did not ask to keep real-estate data, and nothing was deleted from the database | Old data is orphaned until dropped by hand | Migration script |
| 19 | `getFavorites` and `getVisited` keep their names (now return events); the organizer listing is `getAgentEvents` | Renaming them is a frontend-visible change; `AGENT` stays (#13) | `FRONTEND_MIGRATION.md` and the `product-logic` skill still mention `getSavedEvents` / `getVisitedEvents` / `getOrganizerEvents` | Add aliases |
| 20 | Like and view unique indexes now include the group: `{memberId, refId, group}` | A like on a member and one on an event are different things; the old index ignored the group | An existing database keeps its old two-field unique index until it is dropped by hand | None |
