# Architectural Decisions

| # | Decision | Why | Risks | Alternatives |
|---|---|---|---|---|
| 1 | Do the migration in layers; **rename layer first** with no logic change | Keeps the API deployable at every step and makes each diff reviewable | Names of the old catalog and role stay misleading until layer 3 | One big-bang rewrite: faster on paper, hard to debug |
| 2 | Keep GraphQL operations and **MongoDB collections unchanged** in layer 1 | Existing clients and data keep working; no migration script | Frontend still sees the old names | Rename now plus a data migration: cleaner, riskier |
| 3 | Use `git mv` for the app folders | Preserves file history across the rename | None meaningful | Copy and delete: loses blame |
| 4 | Keep the `apps/<name>/src/libs` structure and absolute `apps/...` imports | Changing structure is out of scope for a rename | Absolute imports tie code to the folder name (they had to be edited) | Extract a top-level `libs/` with path aliases; do it later with layer 2 |
| 5 | Fix the batch e2e spec to import `BatchModule` | The spec referenced `NestarBatchModule`, which never existed, so tsc already failed on it | The spec may still not pass at runtime (needs Mongo); only compilation was checked | Delete the spec |
| 6 | Run lint **without `--fix`** | `npm run lint` rewrites files; the baseline has 2379 prettier errors that would pollute a rename diff | Lint debt remains | Run prettier over the repo as its own commit (recommended later) |
| 7 | Leave `.env` keys/values alone | No Nestar strings in it; changing DB names would point at different data | None | Rename DB names with a migration |
| 8 | Git identity stays `Kenneth <avazqudratovv@gmail.com>` (global git config), separate from the Claude account email | Commits should match the GitHub account; the signup email is not a git identity | Commits may not link to the GitHub profile if that email is not added to the account | Set a repo-local `user.email` |
| 9 | Treat the target as **Ticketzy** (the request text said "Petoria") | Repo, remote and package name are Ticketzy | If Petoria is a real second rename, the docs need updating | Ask before proceeding |
| 10 | The old catalog entity becomes **Event + Venue + TicketType** (done) | Price tiers and capacity do not fit a single listing price; locations should be entities, not a city enum | Large change touching DTOs, sort whitelists, `$lookup`s, batch jobs | Reuse the old entity with renamed fields: smaller, but keeps the wrong data model |
| 11 | The old seller role becomes **Organizer** (done, see #13) | Same "owner of the catalog entries" role | `MemberType` enum change affects `RolesGuard`, JWT contents and the frontend | Keep AGENT internally and alias in the UI |
| 12 | Order/Ticket need **atomic inventory** (planned) | No inventory logic exists; overselling is the main ticketing risk | Needs conditional `findOneAndUpdate` or transactions (replica set) | Optimistic checks only: race conditions |
| 13 | **`MemberType` is `USER / ORGANIZER / ADMIN`**: `AGENT` was renamed to `ORGANIZER` (supersedes the earlier "keep AGENT" decision). `events.organizerId` references a member of type `ORGANIZER`. Organizers carry an approval status: `MemberStatus` = PENDING, ACTIVE, REJECTED, SUSPENDED, DELETE (`BLOCK` is gone) | Explicit instruction from the owner for the Ticketzy security and auth milestone | Existing documents with `memberType: 'AGENT'` or `memberStatus: 'BLOCK'` are no longer valid enum values and need a one-off data update | Keep AGENT and alias it in the UI |
| 14 | Event enums: `EventCategory` = CONCERT, SPORT, THEATER, CONFERENCE, FESTIVAL, OTHER; `EventStatus` = DRAFT, PUBLISHED, ON_SALE, SOLD_OUT, CANCELLED, FINISHED, DELETE (superseded by #35); `VenueType` = STADIUM, THEATER, CLUB, HALL, OPEN_AIR, ONLINE; `VenueStatus` = ACTIVE, CLOSED, DELETE. Ticket enums: `TicketTypeStatus` = ACTIVE, PAUSED, SOLD_OUT; `TicketCurrency` = USD, EUR, KRW, UZS; `OrderStatus` = PENDING, PAID, CANCELLED, EXPIRED, REFUNDED; `TicketStatus` = VALID, USED, REFUNDED, CANCELLED; `PaymentProvider` = MANUAL, STRIPE, PAYME, CLICK; `PaymentStatus` = INITIATED, CAPTURED, FAILED, REFUNDED | Taken from the owner's ER diagram | Values are first proposals; adding values later is cheap, removing them is not | Free-text categories |
| 15 | Locations are `venues` documents, not an enum; events filter by `venueId` or `cityList` (resolved through venues) | A city enum cannot hold addresses or capacity | One extra lookup per list | Keep a city enum |
| 16 | (superseded by #48) Payments are a **manual stub** in this milestone: `payOrder` flips PENDING to PAID and writes a `MANUAL` payment | No provider chosen; keeps the inventory and ticket flow testable | Anyone who can call `payOrder` on their own order gets tickets; a real provider webhook must replace it before production | Integrate a provider now |
| 17 | Stock is held by incrementing `ticketTypes.soldQuantity` in one conditional `findOneAndUpdate` (stock, ACTIVE status, sale window and `maxPerOrder` all in the filter). PENDING orders hold stock for 15 minutes (`ORDER_HOLD_MINUTES`, now `SEAT_HOLD_SECONDS`, see #46); the batch job expires them and releases it | Prevents overselling without transactions or a replica set | `soldQuantity` includes unpaid holds | A separate `reservedQuantity` field |
| 18 | The collection and upload folder of the old catalog are **left untouched**; new collections start empty, no migration | Owner did not ask to keep that data, and nothing was deleted from the database | Old data is orphaned until dropped by hand | Migration script |
| 19 | `getFavorites` and `getVisited` keep their names (now return events); the organizer listing is `getOrganizerEvents` (renamed from the old agent name in #27) | Renaming `getFavorites` and `getVisited` is a frontend-visible change | None; the docs and the `product-logic` skill now use these names | Add aliases |
| 20 | Like and view unique indexes now include the group: `{memberId, refId, group}` | A like on a member and one on an event are different things; the old index ignored the group | An existing database keeps its old two-field unique index until it is dropped by hand | None |
| 21 | The `auths` collection (SMS login codes from Nestar, Eskiz) is **dropped from the ER**; the ER has 14 collections | No schema and no code use it; login is phone and password through `members` | If SMS verification is wanted later it needs a new schema and flow | Keep the collection |
| 22 | Notifications are best-effort: `createNotification` swallows its own errors, never notifies people about their own LIKE or COMMENT, and ORDER_PAID goes to both buyer and organizer | A failed notification must not break a like, comment or payment | A lost notification is only logged | Throw and let the caller fail |
| 23 | Roles are set only by the server: `signupUser` creates an ACTIVE USER, `signupOrganizer` a PENDING ORGANIZER, and ADMIN exists only through `npm run seed` (`ADMIN_EMAIL`, `ADMIN_PASSWORD`; inserts one admin only when none exists). `memberType` and `memberStatus` are not part of any signup input, and `updateMember` ignores them | A client-chosen `memberType` let anyone register as ADMIN | Seed needs `.env` access to the database | Admin approval flow for admins |
| 24 | Login is by `memberEmail` (required, unique, lowercase, trimmed). Unknown email and wrong password give one message (`WRONG_EMAIL_OR_PASSWORD`, 401); DELETE, REJECTED and SUSPENDED accounts get `ACCOUNT_NOT_VERIFIED` (401) only after the password matched; PENDING organizers can log in. `memberNick` and `memberPhone` are optional. `memberEmail` is only returned to the member themselves and to admins | No account enumeration; email is private data | Existing members have no email and the unique index will fail to build until they get one | Expose email publicly |
| 25 | JWT carries only `{ _id, memberType }` and lives 1 day. `AuthGuard`, `RolesGuard` and `WithoutGuard` load the member from the database on every request, so suspensions and role changes apply at once. `ActiveOrganizerGuard` (after `RolesGuard`) blocks non-ACTIVE organizers from organizer mutations (`createEvent`, `updateEvent`, `createVenue`, `updateVenue`, `createTicketType`, `updateTicketType`, `checkInTicket`) | Stale 30 day tokens kept blocked users and old roles alive | One extra database read per authenticated request; no refresh tokens yet | Longer tokens with a deny list |
| 26 | Startup validates `SECRET_TOKEN` and the Mongo URI (`MONGO_DEV`, or `MONGO_PROD` in production) and crashes if missing; CORS is limited to `CLIENT_URL`; playground and introspection are off when `NODE_ENV=production`; `ValidationPipe({ whitelist: true, transform: true })` is global (every input field needs a class-validator decorator or it is stripped); uploads are accepted by magic bytes (png, jpeg) and stored with a server-chosen extension | Security hardening milestone | `CLIENT_URL` unset in production means no browser origin is allowed | Keep `origin: true` |
| 27 | The community board (board-article module, DTOs, enum, schema, sort whitelist) is **deleted**, together with `ARTICLE` in the like, view, comment and notification enums, `articleId` in notifications and the `article` upload target. The agent-named operations are renamed to organizer ones: `getAgents` to `getOrganizers`, `AgentsInquiry` to `OrganizersInquiry`, `getAgentEvents` to `getOrganizerEvents`, `AgentEventsInquiry` to `OrganizerEventsInquiry`, `availableAgentSorts` to `availableOrganizerSorts`, `batchTopAgents` to `batchTopOrganizers` (ranking no longer counts articles) | A community board has no place in ticket selling; names now match the role | Existing board data (collection, likes, views, comments, notifications, `uploads/article/`) is orphaned; frontend operation names changed | Keep the board |
| 28 | `CommentGroup` has one value, `EVENT`: comments exist on events only, `getComments` reads only event comments | Member and article comments are gone | Old comments of other groups stay in the database but are never read | Keep MEMBER comments |
| 29 | `subscribe` accepts only ACTIVE members of type ORGANIZER (`ONLY_ORGANIZERS_CAN_BE_FOLLOWED`); `unsubscribe` never looks the target up, so followers can always leave; follower and following lists show only ACTIVE members, filtered before pagination | Following is for organizers; a suspended organizer must not trap followers | Older follows of non-organizers remain until removed | Follow any member |
| 30 | Public visibility: `getMember` and `getOrganizers` return ACTIVE members only (a member can still open their own page while PENDING); `getEvents`, `getEvent`, `getFavorites`, `getVisited` and `likeTargetEvent` hide events whose organizer is not ACTIVE (filtered before pagination, one extra `$lookup` per list). `getTicketTypes` and `createOrder` follow the same rule (#34) | A rejected or suspended organizer must disappear from public pages | Listing cost grows with the number of matched events | Denormalize the organizer status onto events |
| 31 | Organizer approval is done by six ADMIN operations in the new `organizer` module. Allowed transitions (`organizerTransitions` in `member.enum.ts`): verify PENDING to ACTIVE; reject PENDING to REJECTED (reason required, saved in `rejectReason`); suspend ACTIVE to SUSPENDED (reason required, kept in the audit log and the notification); reinstate SUSPENDED or REJECTED to ACTIVE (clears `rejectReason`). The change is one conditional `findOneAndUpdate` on the allowed starting statuses, so two admins cannot both succeed; a refused change answers `INVALID_STATUS_TRANSITION`, a blank reason answers `REJECT_REASON_REQUIRED` / `SUSPEND_REASON_REQUIRED` / `COMMISSION_REASON_REQUIRED`. `updateMemberByAdmin` refuses status or role changes on organizers (`USE_ORGANIZER_OPERATIONS`) so nothing bypasses the audit log | The owner asked for admin approval with reasons; a status machine keeps the states consistent | USER status changes still go through `updateMemberByAdmin` and are not audited yet | A free-form status setter |
| 32 | `commissionOverride { rate, endsAt, reason }` on `Member`: `rate` is a percentage from 0 to 100, `endsAt` is optional and must be in the future when set. It is only stored: no order or payment code reads it yet. `rejectReason` and `commissionOverride` (like `memberEmail`) are returned only to the member themselves and to admins | Commission per order is a planned feature; the override must not leak publicly | No operation clears an override; the platform default rate does not exist yet | Store it in a separate collection |
| 33 | Every organizer operation writes an `audit_logs` entry (`AuditLog` schema: actorId, action, targetType, targetId, meta, timestamps, index on `createdAt`; read with `getAuditLogsByAdmin`) and notifies the organizer (`NotificationType` gained ORGANIZER_VERIFIED, ORGANIZER_REJECTED, ORGANIZER_SUSPENDED, ORGANIZER_REINSTATED, COMMISSION_UPDATED). Both run after the status change. `NotificationService` never throws; `AuditLogService.record` also never throws (a failed write is logged as an error), because the action is already committed and MongoDB without a replica set has no transaction to roll it back | Audit and notification must not undo or block an admin action | A lost audit entry is only visible in the server log | Throw and leave the status changed |
| 34 | `getTicketTypes` and `createOrder` refuse events whose organizer is not ACTIVE (`NO_DATA_FOUND` and `NOT_ALLOWED_REQUEST`); `getTicketTypes` also answers `NO_DATA_FOUND` for an unknown event instead of an empty list | Closes the gap left in #30 | One extra read per call | Denormalize the organizer status onto events |
| 35 | **`EventStatus` = DRAFT, PENDING, APPROVED, REJECTED, CANCELLED, ENDED** (replaces PUBLISHED, ON_SALE, SOLD_OUT, FINISHED and DELETE). Transitions live in `eventTransitions` (`event.enum.ts`): submit DRAFT or REJECTED to PENDING; approve PENDING to APPROVED; reject PENDING to REJECTED (reason required); cancel APPROVED to CANCELLED (reason required); end APPROVED to ENDED (batch). Clients never send a status: `eventStatus` is gone from `EventInput` and `EventUpdate`. Event-level SOLD_OUT is gone (ticket types still have it); orders need an APPROVED event | The owner asked for admin approval before an event is public; one status per step keeps each change a single conditional update | Existing events keep their old status strings and become invisible and uneditable until migrated (see N15); no sold-out badge on the event | Keep both sets of statuses |
| 36 | Organizer edits: `updateEvent` works in DRAFT and REJECTED (status unchanged) and in APPROVED (goes back to PENDING for a new review). PENDING, CANCELLED and ENDED answer `EVENT_NOT_EDITABLE`. The update is conditional on the status that was checked. `submitEventForApproval` validates title, at least one image, start and end in the future, an ACTIVE venue and at least one ticket type, and answers with the first failure. `updateEventByAdmin` edits content only and never changes the status; `removeEventByAdmin` deletes a DRAFT only (never public, so no orders) | PENDING is locked so the reviewer sees what was submitted; an organizer's edit must not skip the review | An organizer cannot withdraw a PENDING event or delete anything; ticket types of an APPROVED event can still change without a new review | Allow editing PENDING and send it back to DRAFT |
| 37 | Public visibility is one constant, `publicEventStatus` (APPROVED), used by `getEvents`, `getEvent`, `getFavorites`, `getVisited`, `likeTargetEvent` and `createOrder`, on top of the ACTIVE-organizer rule (#30). The owner and admins can open their event by id in any status. `rejectReason`, `cancelReason` and `eventModeration` are returned only to the owner and admins (field resolvers). `eventModeration` is stored only: nothing fills it yet | A pending or rejected event must not leak; moderation data is internal | A hidden event answers `NO_DATA_FOUND`, same as a missing one | A separate public DTO |
| 38 | Admin event operations (`approveEventByAdmin`, `rejectEventByAdmin`, `cancelEventByAdmin`) are one conditional update each, then an `audit_logs` entry (`EVENT_APPROVED`, `EVENT_REJECTED`, `EVENT_CANCELLED`, target type `EVENT`, meta `fromEventStatus`, `toEventStatus`, `reason`) and a notification to the organizer (`NotificationType` has the same three values). Approve also refuses an event whose organizer is the acting admin. Cancel lowers the organizer's `memberEvents` and then calls `refundOrdersForCancelledEvent`, an empty hook for the refund task (N5, N14) | Same pattern as organizer approval (#31, #33) | Cancelling does not touch orders or tickets yet | Build refunds in this task |
| 39 | `completedEvents` on `Member`: the batch job `batchEndEvents` (hourly at minute 30) moves APPROVED events whose `endAt` passed to ENDED with a conditional update and adds 1 to the organizer's counter. The counter is a separate write: if it fails the event is still ENDED and the failure is logged | The update filter makes the count happen once per event even if two runs overlap | A lost increment is not retried | A transaction (needs a replica set) |
| 40 | `getOrganizerEvents` is renamed `getMyEvents` and `getAllEventsByAdmin` is renamed `getEventsByAdmin` (with filters status, categories, organizer, text over title and translated titles). `getMyEvents` stays on `RolesGuard` only, so an organizer who is suspended can still see their events and reject reasons; the write operations use `ActiveOrganizerGuard` | Names asked for in the task; reading your own data is harmless | Frontend-visible rename | Keep both names |
| 41 | `Venue.venueLayout` is `{ sections[] }` (key, name, kind SEATED/STANDING, rows, seatsPerRow, capacity for STANDING, x, y, rotation, spacing, tierKey); `venueCapacity` is computed by the server (seated: rows x seatsPerRow, standing: capacity) and removed from `VenueInput`/`VenueUpdate`. `venueTimezone` is an IANA string, default `Asia/Seoul`. Validation is the pure `getVenueLayoutError` in `libs/venue-layout.ts` | The client must not be able to lie about capacity; one pure function is easy to test | `venueLayout` is required on create but optional in the schema (venues created earlier have none and can host GENERAL events only). SEATED sections also need a `tierKey` (needed for matching), rows and seatsPerRow are validated for STANDING sections too | Store capacity as sent: rejected |
| 42 | A `tierKey` links ticket types to layout sections; one ticket type per `tierKey` per event (partial unique index), and several SEATED sections may share a tier. For RESERVED events `totalQuantity` is the sum of seats of the tier's SEATED sections and sending it is refused; the tier key is locked once seats exist | Every seat then has exactly one ticket type and quantity cannot drift from the seats | Refusing (not ignoring) a client quantity can surprise a client that always sends it | Silently overwrite the client value |
| 43 | `EventSeat` (collection `eventSeats`, unique `(eventId, sectionKey, row, number)`, index `(eventId, seatStatus)`) is generated by `approveEventByAdmin` for RESERVED events from the venue layout, using chunked `bulkWrite` upserts with `$setOnInsert` (ordered: false). Seats are generated before the status change, after a pre-check of the transition; a missing tier or duplicate tier fails the approval and changes nothing. Rows and numbers are numbers counted from 1; a retry never creates duplicates and never resets a HELD or SOLD seat. Approval also sets each ticket type's `totalQuantity` to its seat count | Generating after approval could leave an approved event without seats; upserts are idempotent without relying on error codes | No transaction, so when the status change loses a race the seats stay (harmless: they are idempotent). Editing the venue layout after seats exist is not blocked yet | `insertMany` and swallow duplicate-key errors; row letters |
| 44 | `getEventSeatMap(eventId)` is public for APPROVED events of ACTIVE organizers; it returns `venueLayout`, `venueTimezone` and only SOLD seats and HELD seats with `heldUntil` in the future (no `heldBy`, no `orderId`). GENERAL events and venues without a layout answer NO_DATA_FOUND. `submitEventForApproval` checks that a RESERVED event has a seated section and a ticket type for every seated tier; `getMyEvents` now also uses `ActiveOrganizerGuard` | Free seats are implied, so the payload stays small; hold owners are private | Expired holds still show as HELD in the database until a later cleanup job frees them | Return all seats |
| 45 | **Seat holds**: `holdSeats(eventId, seatIds[])` (ACTIVE members of any role, 1 to 8 seats, APPROVED RESERVED event of an ACTIVE organizer that has not started) claims each seat with one conditional `findOneAndUpdate` (AVAILABLE, or HELD with `heldUntil` in the past, or HELD by the same member). If one seat fails, the seats claimed in that call are released and `SEAT_JUST_TAKEN` is thrown. The member's earlier holds on the event that are not in the new request are released first. `releaseSeats(eventId)` frees the caller's own holds. Hold length is `SEAT_HOLD_SECONDS` (optional, default 30, whole number 1 to 3600, validated at startup by `validateEnv`) | The conditional update is the only thing that can decide a race without transactions | Previous holds are released before the claim, so a failed request also loses the holds the member had | Release after a successful claim: keeps the old holds on failure, but briefly holds more than 8 seats |
| 46 | **Orders**: `OrderStatus` is PENDING_PAYMENT (was PENDING), PAID, FAILED, CANCELLED, EXPIRED, REFUNDED. `createOrder` is now `createCheckout(input: { eventId, seatIds? , items? })` and `cancelOrder` is `cancelPendingOrder` (the names asked for). RESERVED orders carry `seatIds` and expire with the earliest `heldUntil`, no stock is touched (the seats are the stock); GENERAL orders reserve stock with the existing conditional update and expire after `SEAT_HOLD_SECONDS` (`ORDER_HOLD_MINUTES` is gone). The client never sends a price: unit prices come from the ticket types, and `subtotal`, `commissionRate`, `commissionAmount`, `totalAmount` are computed and stored on the order | Server-side pricing; one hold clock for both seating types | A 30 second payment window is short; raise `SEAT_HOLD_SECONDS` for real users. Frontend-visible renames | Keep the old names and add new ones |
| 47 | **Commission** (`libs/commission.ts`): an organizer's `commissionOverride` wins while it has no `endsAt` or `endsAt` is in the future; otherwise 10 percent, 7 percent from 5 `completedEvents`, 5 percent from 20 (a count of exactly 5 or 20 already gets the lower rate). The commission is taken out of the organizer's share: the buyer pays the subtotal, so `totalAmount` equals `subtotal`. The rate and amount are rounded to 2 decimals and stored on the order, so later rate changes never touch old orders | The task asked for the rate and amount on the order; it did not say who pays. Deducting from the organizer needs no extra fee line for the buyer | If the platform should add a buyer fee instead, `calculateOrderAmounts` is the one place to change (`total = subtotal + commissionAmount`) | Charge the buyer on top |
| 48 | **Payment** goes through the `PaymentProvider` interface (`charge`, `refund`), injected with the `PAYMENT_PROVIDER` token; `MockPaymentProvider` is bound in `PaymentModule` and never moves money (`PaymentProvider.MOCK` was added to the enum, the `MANUAL` stub of #16 is replaced). `payOrder(orderId, simulate: SUCCESS | FAILURE)`: a PAID order is returned unchanged (idempotent); otherwise charge, then on FAILURE release seats or stock and mark FAILED (a FAILED `Payment` is recorded); on SUCCESS one conditional update per seat (HELD by the buyer, `heldUntil` in the future) to SOLD with `orderId`, and if any fails the seats sold in that call go back to HELD, the charge is refunded and `HOLD_EXPIRED` is thrown, the order stays PENDING_PAYMENT. Then the order is marked PAID (conditional on PENDING_PAYMENT), the `Payment` is recorded and the tickets are created; if that fails everything is undone so the buyer can retry. An order past `expiresAt` becomes EXPIRED and fails with `HOLD_EXPIRED` | `simulate` is only for the mock; a real provider ignores it. A failed seat sale does not mark the order EXPIRED because a parallel `payOrder` of the same order may still be finishing | Anyone can still pay their own order for free until a real provider replaces the mock (N1) | Mark the order EXPIRED on a seat failure: could expire an order that a parallel call just paid |
| 49 | **Tickets**: one `Ticket` per seat or per purchased quantity, with `qrToken` = HMAC-SHA256(ticket id, `QR_SECRET`) as hex and a random `ticketCode`; `seatId` is stored for seated tickets. `QR_SECRET` is required and checked at startup (the API refuses to start without it). `getMyTickets(input: { page, limit, timeFilter? })` filters UPCOMING (event not ended) or PAST before paging and joins event, ticket type and seat; `getTicket(ticketId)` is owner-only. `qrToken` is never returned by `checkInTicket` | The token is only useful if the owner is the only one who gets it | `checkInTicket` still takes the `ticketCode`; nothing verifies the QR token at the gate yet (`verifyQrToken` exists) | Sign with `SECRET_TOKEN`: one leaked secret would break both |
| 50 | **Batch**: `batchExpireOrders` (every minute, extended, not duplicated) sets expired PENDING_PAYMENT orders to EXPIRED, releases their seats (only the buyer's own holds whose `heldUntil` has passed, so a newer hold of the same seat survives) or stock, then resets every HELD seat with a past `heldUntil` to AVAILABLE. Holds are also honoured lazily: a claim accepts a seat whose hold ran out and the seat map hides it, so the sweep only keeps the data tidy | Correctness never depends on the cron timing | Up to a minute of lag before stock of an expired GENERAL order is back | A shorter cron |
| 51 | `updateVenue` refuses `venueLayout` (`VENUE_LAYOUT_LOCKED`) when any non-DRAFT event using the venue already has generated `EventSeat`s; all other venue fields stay editable. The lock is "layout present in the input", so a client that wants to rename the venue must not resend the layout | Seats are copies of the layout taken at approval; changing the layout under them would break the map | Check and update are two steps: an approval at the same moment could slip through | Compare the new layout with the stored one |
