# Architectural Decisions

| # | Decision | Why | Risks | Alternatives |
|---|---|---|---|---|
| 1 | Do the migration in layers; **rename layer first** with no logic change | Keeps the API deployable at every step and makes each diff reviewable | Names of the old catalog and role stay misleading until layer 3 | One big-bang rewrite: faster on paper, hard to debug |
| 2 | Keep GraphQL operations and **MongoDB collections unchanged** in layer 1 | Existing clients and data keep working; no migration script | Frontend still sees the old names | Rename now plus a data migration: cleaner, riskier |
| 3 | Use `git mv` for the app folders | Preserves file history across the rename | None meaningful | Copy and delete: loses blame |
| 4 | Keep the `apps/<name>/src/libs` structure and absolute `apps/...` imports | Changing structure is out of scope for a rename | Absolute imports tie code to the folder name (they had to be edited) | Extract a top-level `libs/` with path aliases; do it later with layer 2 |
| 5 | Fix the batch e2e spec to import `BatchModule` | The spec referenced `NestarBatchModule`, which never existed, so tsc already failed on it | The spec may still not pass at runtime (needs Mongo); only compilation was checked | Delete the spec (done by #99) |
| 6 | Run lint **without `--fix`** | `npm run lint` rewrites files; the baseline had 2379 prettier errors when this was decided (17,185 counted on 2026-10-13: the code is tab-indented and `.prettierrc` says spaces, C3-9) and they would pollute a rename diff | Lint debt remains | Run prettier over the repo as its own commit (recommended later) |
| 7 | Leave `.env` keys/values alone | No Nestar strings in it; changing DB names would point at different data | None | Rename DB names with a migration |
| 8 | Git identity stays `Kenneth <avazqudratovv@gmail.com>` (global git config), separate from the Claude account email | Commits should match the GitHub account; the signup email is not a git identity | Commits may not link to the GitHub profile if that email is not added to the account | Set a repo-local `user.email` |
| 9 | Treat the target as **Ticketzy** (the request text said "Petoria") | Repo, remote and package name are Ticketzy | If Petoria is a real second rename, the docs need updating | Ask before proceeding |
| 10 | The old catalog entity becomes **Event + Venue + TicketType** (done) | Price tiers and capacity do not fit a single listing price; locations should be entities, not a city enum | Large change touching DTOs, sort whitelists, `$lookup`s, batch jobs | Reuse the old entity with renamed fields: smaller, but keeps the wrong data model |
| 11 | The old seller role becomes **Organizer** (done, see #13) | Same "owner of the catalog entries" role | `MemberType` enum change affects `RolesGuard`, JWT contents and the frontend | Keep AGENT internally and alias in the UI |
| 12 | Order/Ticket need **atomic inventory** (planned) | No inventory logic exists; overselling is the main ticketing risk | Needs conditional `findOneAndUpdate` or transactions (replica set) | Optimistic checks only: race conditions |
| 13 | **`MemberType` is `USER / ORGANIZER / ADMIN`**: `AGENT` was renamed to `ORGANIZER` (supersedes the earlier "keep AGENT" decision). `events.organizerId` references a member of type `ORGANIZER`. Organizers carry an approval status: `MemberStatus` = PENDING, ACTIVE, REJECTED, SUSPENDED, DELETE (`BLOCK` is gone) | Explicit instruction from the owner for the Ticketzy security and auth milestone | Existing documents with `memberType: 'AGENT'` or `memberStatus: 'BLOCK'` are no longer valid enum values and need a one-off data update | Keep AGENT and alias it in the UI |
| 14 | Event enums: `EventCategory` = CONCERT, SPORT, FOOTBALL, COMEDY, THEATER, CONFERENCE, FESTIVAL, OTHER (FOOTBALL and COMEDY added later; SPORT kept because removing values is not cheap); `EventStatus` = DRAFT, PUBLISHED, ON_SALE, SOLD_OUT, CANCELLED, FINISHED, DELETE (superseded by #35); `VenueType` = STADIUM, THEATER, CLUB, HALL, OPEN_AIR, ONLINE; `VenueStatus` = ACTIVE, CLOSED, DELETE. Ticket enums: `TicketTypeStatus` = ACTIVE, PAUSED, SOLD_OUT; `TicketCurrency` = USD, EUR, KRW, UZS; `OrderStatus` = PENDING, PAID, CANCELLED, EXPIRED, REFUNDED; `TicketStatus` = VALID, USED, REFUNDED, CANCELLED; `PaymentProvider` = MANUAL, STRIPE, PAYME, CLICK; `PaymentStatus` = INITIATED, CAPTURED, FAILED, REFUNDED | Taken from the owner's ER diagram | Values are first proposals; adding values later is cheap, removing them is not | Free-text categories |
| 15 | Locations are `venues` documents, not an enum; events filter by `venueId` or `cityList` (resolved through venues) | A city enum cannot hold addresses or capacity | One extra lookup per list | Keep a city enum |
| 16 | (superseded by #48) Payments are a **manual stub** in this milestone: `payOrder` flips PENDING to PAID and writes a `MANUAL` payment | No provider chosen; keeps the inventory and ticket flow testable | Anyone who can call `payOrder` on their own order gets tickets; a real provider webhook must replace it before production | Integrate a provider now |
| 17 | Stock is held by incrementing `ticketTypes.soldQuantity` in one conditional `findOneAndUpdate` (stock, ACTIVE status, sale window and `maxPerOrder` all in the filter). PENDING orders hold stock for 15 minutes (`ORDER_HOLD_MINUTES`, now `SEAT_HOLD_SECONDS`, see #46); the batch job expires them and releases it | Prevents overselling without transactions or a replica set | `soldQuantity` includes unpaid holds | A separate `reservedQuantity` field |
| 18 | The collection and upload folder of the old catalog are **left untouched**; new collections start empty, no migration | Owner did not ask to keep that data, and nothing was deleted from the database | Old data is orphaned until dropped by hand | Migration script |
| 19 | `getFavorites` and `getVisited` keep their names (now return events); the organizer listing is `getOrganizerEvents` (renamed from the old agent name in #27) | Renaming `getFavorites` and `getVisited` is a frontend-visible change | None; the docs and the `product-logic` skill now use these names | Add aliases |
| 20 | Like and view unique indexes now include the group: `{memberId, refId, group}` | A like on a member and one on an event are different things; the old index ignored the group | An existing database keeps its old two-field unique index until it is dropped by hand | None |
| 21 | The `auths` collection (SMS login codes from Nestar, Eskiz) is **dropped from the ER**; the ER has 14 collections | No schema and no code use it; login is phone and password through `members` | If SMS verification is wanted later it needs a new schema and flow | Keep the collection |
| 22 | Notifications are best-effort: `createNotification` swallows its own errors, never notifies people about their own LIKE or COMMENT, and ORDER_PAID goes to both buyer and organizer | A failed notification must not break a like, comment or payment | A lost notification is only logged | Throw and let the caller fail |
| 23 | Roles are set only by the server: `signupUser` creates an ACTIVE USER, `signupOrganizer` a PENDING ORGANIZER, and ADMIN exists only through `npm run seed` (`ADMIN_EMAIL`, `ADMIN_PASSWORD`; inserts one admin only when none exists). `memberType` and `memberStatus` are not part of any signup input, and `updateMember` ignores them | A client-chosen `memberType` let anyone register as ADMIN | Seed needs `.env` access to the database | Admin approval flow for admins |
| 24 | Login is by `memberEmail` (required, unique, lowercase, trimmed). Unknown email and wrong password give one message (`WRONG_EMAIL_OR_PASSWORD`, 401); DELETE, REJECTED and SUSPENDED accounts get `ACCOUNT_NOT_VERIFIED` only after the password matched (code and status changed by #64: it is a `GraphQLError` code, GraphQL answers 200); PENDING organizers can log in. `memberNick` and `memberPhone` are optional. `memberEmail` is only returned to the member themselves and to admins | Login does not reveal whether an email exists (sign-up still does: it answers `USED_MEMBER_EMAIL_NICK_OR_PHONE`, an accepted trade-off, C3-40); email is private data | Existing members have no email and the unique index will fail to build until they get one | Expose email publicly |
| 25 | JWT carries only `{ _id, memberType }` and lives 1 day. `AuthGuard`, `RolesGuard` and `WithoutGuard` load the member from the database on every request, so suspensions and role changes apply at once. `ActiveOrganizerGuard` (after `RolesGuard`) blocks non-ACTIVE organizers from organizer mutations (`createEvent`, `updateEvent`, `createVenue`, `updateVenue`, `createTicketType`, `updateTicketType`, `checkInTicket`) | Stale 30 day tokens kept blocked users and old roles alive | One extra database read per authenticated request; no refresh tokens yet | Longer tokens with a deny list |
| 26 | Startup validates `SECRET_TOKEN` and the Mongo URI (`MONGO_DEV`, or `MONGO_PROD` in production) and crashes if missing; CORS is limited to `CLIENT_URL`; playground and introspection are off when `NODE_ENV=production`; `ValidationPipe({ whitelist: true, transform: true })` is global (every input field needs a class-validator decorator or it is stripped); uploads are accepted by magic bytes (png, jpeg) and stored with a server-chosen extension | Security hardening milestone | `CLIENT_URL` unset in production means no browser origin is allowed | Keep `origin: true` |
| 27 | The community board (board-article module, DTOs, enum, schema, sort whitelist) is **deleted**, together with `ARTICLE` in the like, view, comment and notification enums, `articleId` in notifications and the `article` upload target. The agent-named operations are renamed to organizer ones: `getAgents` to `getOrganizers`, `AgentsInquiry` to `OrganizersInquiry`, `getAgentEvents` to `getOrganizerEvents`, `AgentEventsInquiry` to `OrganizerEventsInquiry`, `availableAgentSorts` to `availableOrganizerSorts`, `batchTopAgents` to `batchTopOrganizers` (ranking no longer counts articles) | A community board has no place in ticket selling; names now match the role | Existing board data (collection, likes, views, comments, notifications, `uploads/article/`) is orphaned; frontend operation names changed | Keep the board |
| 28 | `CommentGroup` has one value, `EVENT`: comments exist on events only, `getComments` reads only event comments | Member and article comments are gone | Old comments of other groups stay in the database but are never read | Keep MEMBER comments |
| 29 | **Removed by #122.** `subscribe` accepts only ACTIVE members of type ORGANIZER (`ONLY_ORGANIZERS_CAN_BE_FOLLOWED`); `unsubscribe` never looks the target up, so followers can always leave; follower and following lists show only ACTIVE members, filtered before pagination | Following is for organizers; a suspended organizer must not trap followers | Older follows of non-organizers remain until removed | Follow any member |

| 31 | Organizer approval is done by six ADMIN operations in the new `organizer` module.
